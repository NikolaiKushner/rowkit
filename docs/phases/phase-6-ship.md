# Phase 6 — Ship, in detail

**Deliverable:** `rowkit@0.1.0` and `@rowkit/tokens@0.1.0` live on npm, installable by a stranger following only the docs
**Estimated effort:** ~6h across 2 sessions
**Prerequisite:** Phase 5 complete. Also already done, back in project setup: npm trusted publisher configured (`NikolaiKushner` / `rowkit` / `release.yml`, `npm publish` allowed), 2FA enabled, both package names reserved with `0.0.0` placeholders.

This phase is short because the expensive parts were paid early. What remains is wiring the release pipeline, one honest pre-flight audit, pressing the button, and verifying the result as a stranger would. The discipline of the phase: **nothing ships that hasn't been consumed from the registry itself.** The tarball you tested in Phase 1's spike came from `npm pack`; this phase tests the real thing end to end.

---

## Session 6.1 — Release engineering

### 1. The release workflow

`.github/workflows/release.yml` — the filename must match the trusted-publisher config **exactly**; a mismatch fails with an unhelpful 404 at publish time.

```yaml
name: Release

on:
  push:
    branches: [main]

concurrency: release-${{ github.ref }}

permissions:
  contents: write # changesets commits version bumps + tags
  pull-requests: write # changesets opens the "Version Packages" PR
  id-token: write # OIDC — this is what replaces the npm token

jobs:
  release:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: pnpm/action-setup@v6
      - uses: actions/setup-node@v7
        with:
          node-version-file: .nvmrc
          registry-url: https://registry.npmjs.org
      - run: npm install -g npm@latest # trusted publishing needs npm 11.5.1+
      - run: pnpm install --frozen-lockfile
      - run: pnpm build # tokens build before ui via workspace order
      - run: pnpm test
      - name: Create release PR or publish
        uses: changesets/action@v1
        with:
          publish: pnpm changeset publish
        env:
          GITHUB_TOKEN: ${{ secrets.GITHUB_TOKEN }}
```

Notes on the parts that bite:

- **No `NPM_TOKEN` anywhere.** That's the point of OIDC trusted publishing — the workflow authenticates itself, provenance attestations are generated by default, and there is no long-lived secret to leak. If any tutorial you cross-reference says to add a token secret, it predates the current setup.
- **How the changesets action behaves:** while unreleased changesets exist on `main`, it opens/updates a **"Version Packages" PR** that consumes the changeset files, bumps versions, and writes changelogs. Merging _that PR_ triggers the run that actually publishes. So publishing is always a deliberate PR merge — a natural human gate with no extra process.
- `pnpm changeset publish` publishes every workspace package with a version not yet on the registry — `rowkit` and `@rowkit/tokens` both, in one motion.
- **`@rowkit/tokens` needs one flag:** scoped packages default to restricted access. Add to its `package.json`:
  ```json
  "publishConfig": { "access": "public" }
  ```
  Without it, the first publish of the scoped package fails with a payment-required error that looks like a billing problem and is actually this.

### 2. Fixed versioning between the packages

Decide it now, in `.changeset/config.json`:

```json
{ "fixed": [["rowkit", "@rowkit/tokens"]] }
```

Both packages always share a version number. The alternative (independent versions) is correct for large monorepos and pure overhead for two packages that release together — "rowkit 0.3.0 uses tokens 0.3.0" is an answer a consumer never has to look up. State it in the PR; it's a real decision.

### 3. Pre-flight audit of `package.json` — the boring list that prevents the bad day

Go field by field on both packages:

| Field                                            | Check                                                                                                                                                                                                                                            |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `version`                                        | Still `0.0.0` placeholder — changesets will bump it; don't hand-edit                                                                                                                                                                             |
| `repository`                                     | `{ "type": "git", "url": "git+https://github.com/NikolaiKushner/rowkit.git", "directory": "packages/ui" }` — **the `directory` field matters in a monorepo**, and the URL must match GitHub exactly or trusted publishing rejects the provenance |
| `files`                                          | `["dist"]` — plus `AGENTS.md` for the ui package (it's generated into the package root; verify it's included)                                                                                                                                    |
| `exports`                                        | The Phase 2 contract: `.`, `./styles.css`, `./nuxt`, `./package.json`. Every path exists in `dist` after a clean build                                                                                                                           |
| `types` / `main`                                 | Redundant with `exports` but some older tooling still reads them; point them at the same files                                                                                                                                                   |
| `peerDependencies`                               | `vue`, `tailwindcss` — correct ranges, not pinned versions                                                                                                                                                                                       |
| `sideEffects`                                    | `["**/*.css"]`                                                                                                                                                                                                                                   |
| `license`, `description`, `keywords`, `homepage` | `homepage: "https://rowkit.dev"`; keywords are npm's search index — `vue`, `vue3`, `component-library`, `datatable`, `typescript`, `tailwindcss`                                                                                                 |
| `engines`                                        | `{ "node": ">=20" }` — matches what CI tests, promises nothing it doesn't                                                                                                                                                                        |

Then the mechanical verification, which catches what eyeballing doesn't:

```bash
pnpm -r exec npm pack --dry-run   # lists every file that would ship — read it
npx publint                        # lints exports map / types / ESM correctness
npx @arethetypeswrong/cli --pack packages/ui   # catches type-resolution footguns
```

`publint` and `attw` take five minutes combined and catch the class of packaging bug that otherwise arrives as a confused GitHub issue three weeks post-launch ("types don't resolve under `moduleResolution: bundler`").

### 4. The README — written for the npm page, not the repo

The npm page renders the package README and it's the second-highest-traffic surface after the docs landing. Rewrite the placeholder now that everything is true:

1. One-sentence positioning (same sentence as everywhere — consistency compounds)
2. **The DataTable GIF.** Convert the Phase 3 screen capture: 480p, <3 MB, 15–20 seconds. This is the npm page's live demo
3. Install + minimal usage snippet that renders something real (a small typed DataTable, not a Button — lead with the differentiator)
4. Feature list, five bullets max, each one true
5. Links: docs, Storybook, GitHub
6. Status line: `v0.x` — API stabilizing toward 1.0, changesets-driven changelog

Badges: version, license, bundle size. Skip build-status and coverage badges — on a v0.1 they're noise.

### 5. Repo hygiene for arrivals

Launch traffic lands on the repo within minutes of the first post. Thirty minutes of preparation:

- **Issue templates** (`.github/ISSUE_TEMPLATE/`): bug report (with a "reproduction link" field — StackBlitz/repo, required) and feature request (with a "have you checked ROADMAP's Considered-not-planned section" checkbox — this genuinely deflects the date-picker requests)
- **`CONTRIBUTING.md`**: dev setup (five commands), the component DoD, the changeset requirement, the stage system. Mostly assembled from CLAUDE.md and ROADMAP — an hour, not a project
- Repo settings: description, `rowkit.dev` as website, topics (`vue`, `vuejs`, `typescript`, `component-library`, `design-system`, `datatable`, `tailwindcss`)
- Enable GitHub Discussions — questions belong there, bugs in issues; deciding this before launch avoids retraining early users

## Session 6.2 — The release itself

### 6. Pre-release verification, in order

```bash
git checkout main && git pull
pnpm install --frozen-lockfile
rm -rf packages/*/dist
pnpm build && pnpm test && pnpm lint && pnpm typecheck
pnpm changeset status   # every accumulated changeset, sanity-check the bump levels
```

`changeset status` should show the accumulated history of Phases 1–4 (roughly fifteen changesets) all resolving to a `minor` bump → `0.1.0`. If anything resolves to `major`, a changeset was mislabeled — fix it now; `0.x` majors confuse everyone.

### 7. Publish

1. Merge the **"Version Packages" PR** that the changesets action has been maintaining. Review it first — this PR _is_ the release: version bumps, assembled changelogs. Read the changelog as release notes and edit changeset texts if any read poorly; this is the last cheap moment to fix them
2. The merge triggers `release.yml` → build → test → `changeset publish` → both packages land on npm with provenance, and git tags are pushed
3. Watch it: `gh run watch`

**If publish fails,** the usual suspects in order: workflow filename mismatch vs trusted-publisher config; `repository.url` mismatch; npm version on the runner too old; scoped package missing `publishConfig.access`. All four are checked above, which is why they're checked above.

### 8. Post-publish verification — as a stranger

The step most releases skip, and the one that matters most. On a machine state as clean as you can manage:

```bash
mkdir /tmp/rowkit-smoke && cd /tmp/rowkit-smoke
npm create vue@latest smoke -- --typescript
cd smoke && npm install && npm i rowkit
```

Then follow **rowkit.dev/guide/installation** — the live site, not your memory — until a styled, sorting DataTable renders. Check:

- [ ] Styles arrive (the Tailwind v4 architecture working from the registry, not the workspace)
- [ ] Types resolve; `column.key` autocompletes against the row type
- [ ] `import { tokens } from '@rowkit/tokens'` works
- [ ] `node_modules/rowkit/AGENTS.md` exists
- [ ] The npm pages render correctly: GIF plays, provenance badge shows ("Built and signed on GitHub Actions")
- [ ] Repeat the install check in a fresh Nuxt app (the SSR path is the one with the plugin steps)

Twenty minutes. If anything fails: fix, add a changeset, merge, let the pipeline cut `0.1.1`. **Never `npm unpublish`** — the 24-hour republish lockout on the name turns a small bug into a launch delay.

### 9. Tag the moment

The pipeline pushed version tags; add the human layer:

```bash
gh release create rowkit@0.1.0 --title "rowkit 0.1.0" --notes-file <(pnpm changeset status --output=- 2>/dev/null || echo "First public release")
```

(Or paste the changelog by hand — it's one release.) A GitHub Release gives arrivals a "what's in this" page and starts the release history that makes the project look maintained, because it is.

## What deliberately stays out of this phase

Phase 7 exists so shipping and announcing don't blur:

- The Upwork portfolio item, the LinkedIn post, Show HN / r/vuejs — all Phase 7
- The one exception: **update your GitHub profile README's rowkit line** from "currently building" to "currently building — v0.1 on npm" with the link. Thirty seconds, and the profile stops under-claiming

Resist announcing the moment the publish goes green. A day of buffer between "it's live" and "look at it" is a day in which the smoke test can catch something quietly.

## Failure modes to watch

**Hand-editing versions.** The moment a version number is typed by hand, changesets' model breaks and the next release double-bumps. Versions are outputs, never inputs.

**Unpublishing in a panic.** A broken 0.1.0 is fixed by a working 0.1.1 twenty minutes later. Unpublish is the only move that makes it worse.

**Skipping the stranger test because "the spike covered it."** The spike tested a packed tarball in Phase 1, against a months-younger codebase, from the workspace. The registry artifact, the current code, and the live docs have never been through one loop together until now.

**Launch-eve feature sneaking.** "While I'm at it, Badge could use one more variant" — no. The phase ships what exists. Anything else is a changeset for 0.2.

**Treating this as the finish line.** It's the starting line — 0.1.0 is the version that makes feedback possible. Phase 7 is where the project starts earning its keep, and it begins tomorrow, not "eventually."
